## Findings

### #1 [P2] A canceled process is displayed as "Not started" [Resolved]

- Status: Resolved
- Location: `source/Brows.ProcessAgent.Windows/Resources/Styles.xaml:163-166` (target revision).
- Problem and trigger: Cancel `ProcessAgent.Start` after startup succeeds. The new default exit/status template treats any null `ExitCode` as "Not started" unless `Starting` or `Running` is true. A canceled, previously running proxy has `Started == true`, `Starting == false`, `Running == false`, and `ExitCode == null`, so the template displays the wrong state indefinitely.
- Impact: The control reports that a process never started even though its PID, start time, and collected output show that it did. This affects the sample's supported Run/Cancel flow as well as consumers using cancellation tokens.
- Evidence: An isolated WPF probe started a real `cmd.exe` through `ProcessAgent`, observed `Started=True` and `Running=True`, canceled the token, and awaited the canceled task. The resulting proxy had `Started=True`, `Running=False`, and no exit code; the visible status TextBlock was "Not started". The execution path is explicit in `source/Brows.ProcessAgent/Diagnostics/ProcessProxy.cs:274-277`: cancellation rethrows before the exit-code assignment at line 285, and the finalizer at lines 318-331 clears `Starting` and `Running` without clearing `Started`.
- Suggested resolution: Only use "Not started" when `Started` is false. Represent the started-but-stopped state without an exit code separately, for example as "Stopped" or an unknown exit status. Do not infer cancellation specifically from these properties, because output failures can also leave the same state.
- Verification: Run a process long enough to cancel it after startup and bind its proxy to the default control. After cancellation completes, confirm that the control no longer shows "Running" or "Not started" and preserves its available PID/start time.
- Resolution: The default exit-code template in `source/Brows.ProcessAgent.Windows/Resources/Styles.xaml` now shows "Not started" only while `Started` is false. A process that started but is neither running nor has an exit code shows "Stopped", with its PID and start time unchanged. A known exit code still takes precedence over every state.
- Resolution verification: Added `ProcessProxyViewTest` in the new `tests/Brows.ProcessAgent.Windows.Tests` project (added to `brows-processagent.slnx`), which renders the real default template against a settable fake proxy. Before the fix, `Status_CanceledAfterStartDoesNotShowNotStartedOrRunning` and `Status_ProcessCanceledWhileViewIsDisplayedUpdatesTheStatus` failed with the visible status "Not started". After the fix they pass, as do the not-started, starting, running, and exit-code-wins cases. A real-process cancellation was also reproduced earlier in an isolated probe (`Started=True`, `Running=False`, `ExitCode=null`). The automated tests use a fake proxy rather than a live process, so the real `ProcessProxy` state transitions are covered only by that probe and by the code trace in the finding.

### #2 [P2] Initial display of an already-started proxy ignores ProcessDateTimeFormat [Resolved]

- Status: Resolved
- Location: `source/Brows.ProcessAgent.Windows/Resources/Styles.xaml:115-120` (target revision).
- Problem and trigger: Set `ProcessProxy` to a proxy with a non-null `StartTime` and set `ProcessDateTimeFormat="HH:mm:ss"` before initializing the control. The new nested start-time presenter renders the default date/time text instead of the requested format. Its `ContentStringFormat` binding eventually becomes active with the correct value, but the rendered text does not refresh.
- Impact: Opening or recreating a view for an existing process produces incorrectly formatted status text and consumes substantially more horizontal space than the configured time-only format. This is a regression from the original control template.
- Evidence: With an en-US proxy start time of `2026-11-15 15:00:00`, the target template rendered `11/15/2026 3:00 PM` while the presenter's active `ContentStringFormat` binding resolved to `HH:mm:ss`. Loading the baseline template with the same proxy and settings rendered `15:00:00`. The target behavior was also reproduced with a real already-started `ProcessAgent` proxy attached to an invisible WPF HWND. When the initial control instead starts with a null start time and receives a start time later, the format takes effect. These observations support an initialization-order problem introduced by resolving the ancestor binding inside the nested data template.
- Suggested resolution: Ensure the formatting input is resolved before the date value is rendered, or explicitly refresh formatted content when the format binding resolves or changes. A formatting converter with both the date and format as inputs is one practical approach. Preserve both initial and later format updates.
- Verification: Initialize a view with an already-started proxy and `HH:mm:ss`; verify that the visible value contains only the requested time. Repeat after replacing/reapplying the template and after changing the format, and also cover a proxy that starts after the view is created.
- Resolution: The start time is now rendered by a `TextBlock` whose text is a `MultiBinding` over `StartTime` and `ProcessDateTimeFormat`, using the new internal `ProcessDateTimeConverter` (`source/Brows.ProcessAgent.Windows/Windows/Data/ProcessDateTimeConverter.cs`). The text is produced from both values together, so it no longer depends on when the nested `ContentStringFormat` binding resolves. A null or empty format uses the general (`G`) format; an invalid format falls back to the default `DateTime` text. This also corrects the null-format default, which previously rendered the short form (for example `11/15/2026 3:04 PM`) instead of `G`.
- Resolution verification: Before the fix, `StartTime_AlreadyStartedProxyUsesTheConfiguredFormatWhenFirstDisplayed`, `StartTime_ChangingTheFormatUpdatesTheDisplayedTime`, and `StartTime_WithoutAFormatUsesTheGeneralFormat` failed, with the visible text `11/15/2026 3:04 PM`; `StartTime_ProxyThatStartsAfterTheViewUsesTheConfiguredFormat` already passed, matching the finding. After the fix all four pass, covering an already-started proxy, a later format change, a later start, and the default format. The converter formats with the binding culture, which is the same default (`en-US` unless `Language` is set) that the original `ContentStringFormat` used.

### #3 [P3] Hidden placeholders do not keep the status columns at stable widths [Resolved]

- Status: Resolved
- Location: `source/Brows.ProcessAgent.Windows/Resources/Styles.xaml:115-121`; related instances at `:136-137` and `:148-156` (target revision).
- Problem and trigger: The overlaid elements reserve the maximum width of their current text, not the width of values that have not arrived yet. Before startup, the timestamp is empty and its placeholder is only an em dash; the PID is similarly empty. When these values become available, their auto-sized columns grow. An exit code wider than the "Not started" placeholder also grows the final column.
- Impact: Status items move and the available command width changes during the lifecycle, contrary to the new documented stable-width behavior. This is an incomplete part of the new stability feature; visible shifting also existed in the baseline.
- Evidence: In a 900-DIP-wide default control using en-US formatting, publishing `StartTime=2026-11-15 15:00:00` and `ProcessID=12345` moved the "Started" label from x=712.72 to x=581.64 (131.08 DIPs). Changing the exit code from null to `-1073741510`, a supported signed process-exit value, moved it again to x=549.80 (another 31.84 DIPs). The exit slot grew from 60.21 to 92.05 DIPs. `Hidden` preserves existing desired sizes, but it does not reserve future timestamp/PID/exit-code text.
- Suggested resolution: Reserve consistent widths across the supported states, accounting for the selected date format, PID size, and signed exit codes, or use another layout that guarantees equivalent space before and after values arrive. Custom status templates with sufficient fixed widths provide a workaround.
- Verification: Measure the same default control before startup, while running, and after short and long signed exit codes. Confirm that each status slot's width and neighboring item positions remain unchanged, including the transition from null timestamp/PID values.
- Resolution: Each status slot now contains an always-hidden element that reserves the width of its widest value: a sample date-time formatted with the configured format for the start time, seven digits for the process ID (right-aligned), and "Exit -2147483648" laid out like the real label for the exit code. The null-state placeholders overlay these. A process ID longer than seven digits, or a custom status template that does not reserve its own width, can still change a slot width; the README now describes this.
- Resolution verification: `Layout_StatusItemsDoNotMoveAsTheProcessStartsAndExits` measures the left edge of the "Started" label before startup, while running, after exit code 0, and after exit code -1073741510. Before the fix it moved from 712.72 to 666.82 DIPs when the process started. After the fix all four positions agree within 0.5 DIP. `Layout_StatusItemsDoNotMoveWhenAProcessIsStoppedAfterItStarted` covers the stopped state. Widths were measured at a 900 DIP view width in a non-windowed WPF harness; the result was not inspected visually in the sample app.
- Later change: At the author's request, the reserve for a signed 32-bit exit code ("Exit -2147483648") was removed because it left the exit slot about 30 DIPs wider than its normal content. The exit slot now reserves the width of "Not started" (the widest state text); exit codes of up to about six digits still fit, and a longer code such as -1073741510 widens the slot once when the process exits. `Layout_StatusItemsDoNotMoveAsTheProcessStartsAndExits` now checks exit code 255 in place of -1073741510. The start-time and process ID reserves are unchanged.
