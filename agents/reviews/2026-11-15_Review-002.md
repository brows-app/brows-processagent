## Findings

### #1 [P3] The timestamp width sample does not reserve enough space for supported formats [Resolved]

- Status: Resolved
- Location: `source/Brows.ProcessAgent.Windows/Windows/Data/ProcessDateTimeConverter.cs:14-15` (target revision); consumed by the hidden reserve at `source/Brows.ProcessAgent.Windows/Resources/Styles.xaml:130-138`.
- Problem and trigger: Set `ProcessDateTimeFormat` to a supported format such as `D`, `MMMM`, or `O`, display the control before the process starts, and then publish its start time. The fixed sample is Monday, December 28, 2026 and has `DateTimeKind.Unspecified`. December/Monday are not the widest month/day names, and the sample omits the time-zone suffix that `O` produces for a local start time. The production proxy sets `StartTime = DateTime.Now`, so the local-kind case is reachable with ordinary real processes.
- Impact: The timestamp auto column grows on startup, moving the status items and reducing the command's available width despite the documented stable-width behavior. The content remains correct; a custom template with an adequate fixed width is a workaround. This is an incomplete part of the branch's new stability feature, not a claim that the baseline had stable layout.
- Evidence: An isolated WPF probe rendered the target theme at 900 DIPs with the default font and en-US binding culture. With `D`, the reserve text was `Monday, December 28, 2026`; publishing local `2026-09-30 15:04:05` rendered `Wednesday, September 30, 2026` and moved the `Started` label from x=507.78 to x=486.60, a 21.18-DIP shift. `MMMM` shifted it 3.54 DIPs. With `O`, the reserve was `2026-12-28T12:28:28.0000000`, while the local value was `2026-09-30T15:04:05.0000000-05:00`, moving the label from x=500.03 to x=466.75, a 33.28-DIP shift. The same probe observed no shift for `HH:mm:ss`. `ProcessProxy.cs` assigns `DateTime.Now` on startup; the converter always substitutes its unspecified-kind sample while `Sample` is true. These are executed layout measurements, not a screenshot-based assessment.
- Suggested resolution: Reserve a width that accounts for the selected format, culture, font, and actual timestamp kind, including localized month/day names and local time-zone suffixes; alternatively expose/use a fixed timestamp slot width with a clear supported-format contract. A single Gregorian date with unspecified kind is not a reliable maximum. Add representative long-date and round-trip cases to the existing layout regression coverage.
- Verification: Measure each status item's position before startup and after publishing local timestamps with `D`, `MMMM`, and `O`, including a Wednesday in September in en-US. Positions should remain unchanged within the existing layout tolerance. Retain the passing `HH:mm:ss`, cancellation, and signed-exit-code cases.
- Resolution: In `source/Brows.ProcessAgent.Windows/Windows/Data/ProcessDateTimeConverter.cs`, the sample used for the hidden width reserve is now the widest result of the configured format across every month and weekday (22nd to 28th of each month in 2026), formatted as a local time at 12:28:28 with the binding culture. It therefore covers the longest localized month and weekday names and the UTC offset that a local time adds to formats such as `O`. Width is estimated by character count, which is exact for numeric formats and an approximation for names in a proportional font. `README.md` now states this instead of promising exact stability for every format.
- Resolution verification: Added `Layout_StatusItemsDoNotMoveForFormatsWhoseWidthVaries` for `D`, `MMMM`, `dddd`, `O`, and `F`, using a local-kind Wednesday 30 September 2026. Before the fix all five failed: the "Started" label moved 21.18 (`D`), 3.54 (`MMMM`), 17.65 (`dddd`), 33.28 (`O`), and 14.71 (`F`) DIPs when the start time arrived, matching the review's measurements. After the fix all five pass within 0.5 DIP, as do the existing `HH:mm:ss`, cancellation, and signed-exit-code cases (18 WPF tests, plus 36 core tests on each of net462, net48, and net10.0). Only en-US was exercised; other cultures and fonts rely on the character-count approximation and were not measured.
