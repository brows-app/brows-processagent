## Findings

### #1 [P3] Exit-code adjacency test fails under cultures that use U+2212 as the minus sign [Resolved]

- Status: Resolved
- Location: `tests/Brows.ProcessAgent.Windows.Tests/Windows/Controls/ProcessProxyViewTest.cs:113-123` (target revision), specifically `exitCode.ToString()` at line 123.
- Problem and trigger: `Layout_ExitCodeIsAdjacentToItsLabel(-1073741510)` locates the rendered exit code with `texts.Single(text => text.Text == exitCode.ToString())`. `ToString()` uses the thread's current culture, but the control's `Text="{Binding ExitCode}"` binding formats with the element's `Language`, which defaults to `en-US`. On .NET 5 and later (ICU culture data), cultures such as `sv-SE`, `nb-NO`, and `fi-FI` use U+2212 MINUS SIGN as `NumberFormatInfo.NegativeSign`, so the expected string is `−1073741510` while the control renders `-1073741510`.
- Impact: The test throws `InvalidOperationException` ("Sequence contains no matching element") on a developer or build machine with such a regional setting. The control behaves correctly; the failure is a false negative that blocks local test runs. CI (`windows-latest`, en-US) is unaffected, which is why it has not surfaced. The `[TestCase(3)]` case is unaffected.
- Evidence: In PowerShell 7.7 on .NET, `NegativeSign` is U+2212 for `sv-SE`, `nb-NO`, and `fi-FI`, and U+002D for `en-US` and `de-DE`. A scratch WPF harness that set `CultureInfo.CurrentCulture = sv-SE`, rendered the default template for a proxy with `ExitCode = -1073741510`, and repeated the test's lookup printed: `rendered '-1073741510' (U+002D); test expects '−1073741510' (U+2212); match=False`, and `Single` threw "Sequence contains no matching element". The other expected strings in the file are culture-neutral: digit-only values, the explicit `HH:mm:ss`/`hh:mm` formats that the control renders with `en-US`, and `StartTime_WithoutAFormatUsesTheGeneralFormat`, which already formats its expectation with `en-US` explicitly.
- Suggested resolution: Format the expected value with the culture the binding uses, for example `exitCode.ToString(view.Language.GetSpecificCulture())`, or `CultureInfo.GetCultureInfo("en-US")` to match the existing start-time test. Alternatively, apply NUnit's `[SetCulture("en-US")]` to the fixture so every expectation is evaluated in the binding's culture.
- Verification: Run `Layout_ExitCodeIsAdjacentToItsLabel` with `CultureInfo.CurrentCulture` set to `sv-SE`, for example by temporarily adding `[SetCulture("sv-SE")]`. It should pass, and it should still pass under `en-US`.
- Resolution: In `tests/Brows.ProcessAgent.Windows.Tests/Windows/Controls/ProcessProxyViewTest.cs`, the check moved into a private helper, `AssertExitCodeIsAdjacentToItsLabel`, which now formats the expected exit code with `view.Language.GetSpecificCulture()`, the culture the binding actually uses, instead of the thread's culture. The control was not changed.
- Resolution verification: Added `Layout_ExitCodeIsAdjacentToItsLabelWhenTheCurrentCultureUsesADifferentMinusSign`, which runs the helper for -1073741510 under `[SetCulture("sv-SE")]`. Before the fix it failed with `InvalidOperationException : Sequence contains no matching element`, reproducing the finding. After the fix it passes, as do the two existing `Layout_ExitCodeIsAdjacentToItsLabel` cases under `en-US` (23 WPF tests, plus 36 core tests on each of net462, net48, and net10.0). Only `sv-SE` was exercised; `nb-NO` and `fi-FI` share its minus sign but were not run separately.
